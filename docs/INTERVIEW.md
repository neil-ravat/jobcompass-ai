# JobCompass interview walkthrough

## Explain the implemented project

JobCompass retrieves published remote jobs through the official Himalayas API,
normalizes the inconsistent external JSON, and stores provenance with each record.
A FastAPI service applies explicit constraints and returns deterministic or
semantic recommendations with component scores and original application links.
PostgreSQL/pgvector and local MiniLM embeddings are working; an optional validated
LLM intent-parser integration exists, but its successful live call is unverified
because credentials were unavailable. Code was generated by Codex; do not describe
it as independently implemented until you have done that work yourself.

## Trace a real request

1. `himalayas.fetch_page()` requests a page with a finite timeout and bounded retry
   policy; it validates the envelope and preserves opaque cursor tokens.
2. `normalize_job()` checks required identity/application fields, maps optional
   values, preserves raw data, uses Decimal for money, and UTC-aware datetimes.
3. `ingest()` deduplicates by source/ID, checks source status, preserves first-seen
   time, and atomically saves a snapshot. Partial runs cannot reconcile absent jobs.
4. `database.upsert_snapshot()` writes parameterized SQL inside a transaction.
   Composite identity prevents duplicate rows; migrations have stored checksums.
5. `semantic.build_index()` embeds title/context using MiniLM. Model identity and
   content hashes catch stale indexes. Real SQL uses pgvector cosine distance.
6. `/recommendations` filters first and ranks by transparent token coverage;
   `/search` combines positive cosine similarity and lexical score. Hard-country,
   salary and freshness constraints cannot be overcome by a high similarity score.
7. `/agent/query` asks an LLM for one structured tool call, validates it, reapplies
   explicit user constraints and invokes the same Python functions. Returned job
   facts come from retrieval, not generated prose.

## Decisions you should be able to defend

- Why preserve missing versus empty location restrictions? Missing means unknown;
  an explicitly empty source array means unrestricted. Confusing them produces
  false eligibility claims.
- Why preserve salary currency and pay period? USD 50 hourly and INR 50 annually
  are not comparable. The MVP performs no invented conversion or annualization.
- Why use Decimal? Binary floating point is unsuitable for exact monetary values.
- Why is an Apply URL different from a source ID? Identity controls deduplication;
  the source-provided link must retain its application/tracking parameters.
- Why not mark every missing job closed? A capped page, network failure or malformed
  record does not establish absence from the full source feed.
- Why two cache lifetimes? Feed refresh and job closure have different freshness
  requirements; per-job status can change before the daily feed refresh.
- What is idempotence? Ingesting the same source identity updates its record rather
  than creating another row; first-seen time remains stable.
- Why use exact vector search? Three records do not justify approximate-index
  complexity. At scale, measure candidate filtering and index recall before HNSW.
- What does the score mean? Lexical coverage or weighted cosine similarity, not
  probability of hiring, suitability certainty or an independently validated grade.
- Why keep the LLM outside hard constraints? Model output is untrusted. Valid JSON
  can still express the wrong intent, so Python validates and enforces explicit
  user requirements and the response exposes the interpretation.

## Read the test evidence correctly

136 tests passed with four real database integration cases. Unit tests replace
source/LLM calls; they do not establish live provider availability. Separate real
API checks verified three source jobs and pgvector retrieval. One regression
caught an expiry resurrection bug; another caught timezone changes on upsert.

Precision@K counts relevant returned results divided by K. NDCG@K discounts
relevant results at lower ranks against an ideal ordering. The current evaluation
uses three jobs, three positive queries and one negative country case, with
Codex-assigned labels. Perfect top-one scores on this set are not evidence of
production accuracy or a semantic improvement over keyword matching.

## Be precise about limitations

Live successful LLM inference, container deployment, large-corpus scale, broad
human relevance review, visa eligibility and timezone compatibility are not
verified. Remote advertising does not mean work-from-anywhere. No applications
are submitted automatically. The next valuable validation task is a larger,
independently labeled corpus after the source's daily refresh, plus one bounded
LLM query if credentials become available.
